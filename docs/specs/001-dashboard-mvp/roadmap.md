# dashboard-mvp — 作業単位への分解

nullops の最初の画面を作る。`wails dev` と macOS の `wails build` の両方で、README「画面」表の 6 パネル(ログストリーム / コミットグラフ / 折れ線グラフ / グラフビュー / タコメータ / 3D 散布図)が 1 画面に並び、擬似ログの流入・グラフの更新・3D 散布図の回転が継続する状態にする。unit の切り方はこの状態から逆算している。

要求の本体はリポジトリの `README.md`「画面」表にある。言語規約・コーディング規約・注意事項は `CLAUDE.md` にある。本書はこれらの内容を再記述せず、見出しで参照する。

## 前提

- 分解は複数 unit へ分ける方針で進める(依頼者が承認済み)。
- 擬似ログ・擬似データの生成は Go 側に実装してフロントエンドへ供給する。genact は表現の参考にとどめ、外部バイナリの同梱と子プロセスの起動をしない(各 OS 向けのビルドと配布を単純に保つため。依頼者が承認済み)。
- 既存の Go 資産は Wails v2 のテンプレートのままである。bind は `App` の 1 メソッド(`Greet`)のみ、ウィンドウは 1024x768・フレーム有り、`frontend/dist` を `embed.FS` で埋め込む。module 名は `nullops`、直接依存は `github.com/wailsapp/wails/v2 v2.13.0` のみ。ルート以外に Go のパッケージディレクトリは無い。
- 既存のフロントエンド資産は Next.js 16 / React 19 / Tailwind CSS 4 / Biome 2.5 で、`next.config.ts` は `output: 'export'`・`distDir: 'dist'` を設定済みであり Wails の埋め込み対象と一致している。画面はテンプレートの Greet ボタンのみで、独自のコンポーネントは無い。
- 可視化・3D の依存(three / d3 / recharts / chart.js 等)は 1 つも入っていない。各パネルの描画手段(ライブラリの採用か自前実装か)は、そのパネルを含む unit の仕様化で確定する。本書では選定しない。
- Go・フロントエンドともテストは 1 件も無く、CI ワークフローも無い。検証はローカルのコマンド(`go vet ./...`・`go test ./...`・`cd frontend && npm run lint`)と、`wails dev` / `wails build` の生成物に対する人間の目視で行う。
- `frontend/node_modules` は未インストールであり、lint・ビルドの前に `cd frontend && npm ci` が要る。
- 作業は git worktree `~/repos/worktrees/nullops-wip-dashboard` のブランチ `wip/dashboard`(main と同一コミット)で行い、各 unit の作業ブランチはここから派生する。
- ホストに Go 1.26.5 / Node v24.16.0 / Wails CLI v2.13.0 が導入済み。
- 知識 port は無い(`docs/dev/ports/` が存在しない)。

## 1. unit 一覧

| #   | unit               | 範囲                                                                                                                                                                  | 依存    |
| :-- | :----------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------ |
| 1   | `dashboard-shell`  | Go 側の擬似データ生成とフロントエンドへの供給の機構、6 枠を 1 画面に並べるレイアウト、ログストリームパネル。あわせて検証の手段(Go のテスト実行・`npm ci` からの lint・`wails build`)を通る状態にする。 | —       |
| 2   | `scatter3d-panel`  | 3D 散布図パネル。擬似点群の生成と 3 次元描画・回転、およびそれに要する描画手段の導入。                                                                                 | 1       |
| 3   | `graph-panels`     | コミットグラフパネルとグラフビューパネル。分岐とマージを含む擬似コミット履歴、およびノードとエッジの擬似依存関係の生成と描画。                                          | 1       |
| 4   | `metrics-panels`   | 折れ線グラフパネルとタコメータパネル(擬似メトリクスの生成と描画)。あわせて 6 パネル同時稼働の調整、配布ビルドでの通し確認、README の記述と実画面の一致確認。                          | 1, 2, 3 |
| 5   | `framestats-runtime` | 6 パネル同時稼働時のフレーム間隔を配布ビルドで実測できるようにする。計測の有効化を実行時に切り替える口を足す(既定は無効)。**当初の分解には無く、#4 の完了後に追加した。** | 4       |

順序は #1 → #2 → #3 → #4 とする。

- #1 を最初に置くのは、検証の手段が現時点で無いためである(テストが 1 件も無く、`node_modules` も未インストールで lint を実行できない)。以降の unit の完了条件を確かめられる状態を #1 で作る。ログストリームを #1 に含めるのは、擬似データの供給機構の最初の利用者であり、かつ「作業中に見える」という企画の中核をなすパネルだからである(共通基盤は、それを最初に使う unit に含める)。
- #2 を #3・#4 より前に置くのは、6 パネルのうち 3D 散布図の不確実性が最も高いためである(WebView 上での WebGL の動作、静的エクスポートでの描画ライブラリの取り込み、同時稼働時の負荷の支配要因)。判断を早く得る。
- #3 を #4 より前に置くのは、コミットグラフとグラフビューがノード・エッジの配置算出という共通の難所を持ち、折れ線グラフ・タコメータより不確実性が高いためである。
- #4 は 6 パネル中で最も単純な 2 枚であり、最後の unit として 6 パネル通しの統合と配布ビルドの確認を担う。統合を独立した unit に分けないのは、その中身(同時稼働の調整・ビルド確認・README への反映)だけでは仕様化と承認の往復に見合わないためである。
- #2 と #3 は依存が #1 のみで、触る対象のパネルが重ならないため並行して進めてよい。#4 は 6 パネル通しの確認を含むため #2・#3 の完了後に着手する。
- #5 は当初の分解に無い。#4 が入れた計測器が開発ビルドでしか動かず、開発ビルドの値では判断できないと分かったため、#4 の完了後に追加した。経緯と却下した手段は `005-framestats-runtime/spec.md` にある。

### 1.1. 各 unit の完了条件

- **`dashboard-shell`**: `wails dev` を起動すると 1 画面に 6 枠が並び、ログストリームの枠に擬似ログが流入する。30 秒間の観察でログ行が増え続ける(途中で停止しない)。ウィンドウを閉じるとアプリのプロセスが終了し、残留しない。`cd frontend && npm ci` の後に `go vet ./...`・`go test ./...`(1 件以上のテストを実行して成功する)・`cd frontend && npm run lint` がいずれもエラーなく終了し、`wails build` が成功する。
- **`scatter3d-panel`**: `wails dev` で 3D 散布図の枠に点群が描画され、回転が継続する。30 秒間の観察で回転が止まらない。ウィンドウを最小化して復帰させた後も描画と回転が続く。`go vet ./...`・`go test ./...`・`cd frontend && npm run lint`・`wails build` が引き続きエラーなく終了する。
- **`graph-panels`**: `wails dev` でコミットグラフの枠に分岐とマージを含む履歴が描画され、新しいコミットが追加されて表示が変化する。グラフビューの枠にノードとエッジが描画され、30 秒間の観察でノード・エッジの増減または個々のノードの表示状態の変化が 1 回以上起きる。`go vet ./...`・`go test ./...`・`cd frontend && npm run lint`・`wails build` が引き続きエラーなく終了する。
- **`metrics-panels`**: `wails dev` で折れ線グラフの枠に時系列が描画されて時間とともに伸び、タコメータの針が値に追従して動く。同じ画面で 6 パネルすべてが同時に更新され続け、30 秒間の観察で停止するパネルが無い。`go vet ./...`・`go test ./...`・`cd frontend && npm run lint` がいずれもエラーなく終了する。macOS で `wails build` が成功し、生成したアプリを起動した画面を人間が確認する。README「画面」表の 6 行と実画面のパネルが 1 対 1 で対応する(対応しない箇所があれば README を更新して一致させる)。

## 2. 未確定

- **「作業中に見える」と言える見た目の水準**: 配色・情報密度・更新の速さがどこまで作り込まれていれば目的を満たすかを、実物を見る前に基準として述べられない。#1 の完了時に実画面を見て初めて問いを立てられる(そこで基準を述べられるようになれば、追い込みを unit として立てるか、各 unit の仕様に織り込むかを判断する)。
- **6 パネル同時稼働時の性能の目標値**: フレームレートと CPU 使用率の閾値を今は数値で述べられない。閾値は 3D 散布図の描画方式に支配されるが、その方式が #2 の仕様化まで決まらないため、達成しうる水準が分からず問いを数値の形にできない。#2 の完了後に述べられるようになる。

## 3. スコープ外

- **Windows・Linux での動作確認**: README は 3 OS を動作環境とするが、今回の確認環境を macOS のみとすることを依頼者が明示した。他 OS での確認は最初の画面を成立させるという目的の外である。
- **6 パネル以外のパネルの追加・画面の切り替え・設定 UI・ウィンドウ位置の保存**: 目的は README「画面」表の 6 パネルを 1 画面に並べることであり、画面の増設と永続化はその外である(依頼者が明示)。
- **配布物の署名・公証と GitHub リリースの作成**: 出荷の工程であり、画面の実装という目的の外である(依頼者が明示)。
- **CI ワークフローの追加**: リポジトリに GitHub Actions のワークフローが無く、検証はローカルのコマンドで行うと依頼者が定めたため。
- **genact バイナリの同梱と子プロセスの起動**: 各 OS 向けのビルドと配布を単純に保つため、擬似データの生成を Go 側の実装に閉じると決定済み(依頼者が承認)。genact は表現の参考としてのみ用いる。
- **実在のシステム情報の読み取りと外部への通信**: 画面に出る値をすべてこのアプリが生成した擬似データとする方針のため(`CLAUDE.md`「注意事項」)。
- **描画の自動視覚検証(ブラウザ自動化等)の整備**: 依頼者が完了条件で人間の目視による確認を定めたため、検証手段の自動化は今回の目的の外である。

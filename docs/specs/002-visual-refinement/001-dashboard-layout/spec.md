# dashboard-layout — 仕様

## 1. 目的と背景

roadmap `001-dashboard-mvp` で 6 パネルは動くようになったが、6 枠を 3 列 2 行に均等に割り、各枠に見出し行を付けた画面は、実在の監視画面より単調に見える(request.md §1)。本 unit は、パネルの見出し行を消し、6 等分をやめて枠ごとに大きさの違う配置へ作り直す(request.md §2.1)。

配置は `research.md` §2 の 4 案のうち **案 D(中央主役型)** をユーザーが選んだ。中央に 3D 散布図、上に折れ線グラフの帯、左にログストリームの縦長、右上にタコメータ、右にグラフビューとコミットグラフを積む。本書は案 D を `DashboardGrid`・`Panel` の契約と README の改訂に落とし、受け入れ基準を定める。

要求の本体は `docs/specs/002-visual-refinement/request.md`(§番号で参照)、unit の範囲と完了条件は `docs/specs/002-visual-refinement/roadmap.md` §1・§1.1、配置案の調査は同ディレクトリの `research.md` にある。本書はそれらを再記述しない。

## 2. スコープ

### 対象(やること)

- 12 列 × 8 行の格子と、6 枠の配置(§6.1)。`DashboardGrid` の契約を「6 個の子要素」から「slot ごとの本文の record」へ変える(§5.1)
- 枠から見出し行(`h2` と区切り線)を消す。`Panel` の契約から `title` を落とし、配置先の `slot` を受け取る(§5.2)
- 組み立て(`frontend/src/app/page.tsx` の `Home`)を新しい契約に合わせる(§5.3)
- README「画面」節の改訂。「枠の題名」列を落とし「位置」列を足し、配置の型を 1 文で述べる(§6.3)
- 配布ビルドの目視と、`wails build -devtools` のビルドでの p95 の計測(Requirement 7)

### 対象外(やらないこと)

- ログストリーム・コミットグラフ・折れ線グラフ・タコメータの描画の中身の変更 — 理由: roadmap §3 が「4 パネルは枠の大きさと位置が変わるだけで描画の中身は変えない」と定めた。ログストリームの折り返し規則・列構成の変更もこれに当たる(§6.4・§8)
- 3D 散布図の軸線・ドラッグ操作・点の形 — 理由: unit `scatter3d-controls`(roadmap §1 #2)の範囲
- 依存グラフのノード数と配置 — 理由: unit `depgraph-density`(roadmap §1 #3)の範囲
- タコメータのダイヤルの複数化 — 理由: 案 D はタコメータを右上の枠に置くため、案 A の帯に伴う論点(`research.md` §3 論点 2)が消えた。`GaugePanel.tsx`・`metricsource.go` は変えない
- ウィンドウの下限(1100×720)付近での配置の切り替え — 理由: ユーザーの決定(`research.md` §3 論点 4 の回答)。下限でも同じ比率で縮む
- 枠線と背景差を消して隙間だけで区切る形 — 理由: ユーザーの決定(同 論点 3 の回答)。枠線と背景差は残す
- README への ASCII 図の掲載 — 理由: ユーザーの決定(同 論点 6 の回答)。表と 1 文で述べる
- 案 A・B・C の採用と再検討 — 理由: ユーザーの決定(同 論点 1 の回答)
- 計測器(`frontend/src/lib/framestats.ts`)の改修 — 理由: roadmap §3
- Windows・Linux での確認 — 理由: request.md §4
- 描画の自動視覚検証 — 理由: roadmap §3。判定は人間の目視で行う

## 3. 前提(未検証の賭け)

1. **各パネルの描画面は、案 D の細長い枠・大きな枠でも枠に追随して破綻しない** — 根拠: Canvas を持つ 5 パネルは `ResizeObserver` で枠の大きさへ追随し、`Scatter3DPanel`・`GaugePanel` は半径を `min(width, height)` 比で決める(`research.md` §1.3)。ログストリームは `h-full` で枠の高さに合わせる。— 検証方法: Requirement 4.1・4.3 を配布ビルドで目視する / 状態: 未検証
2. **配置を変えても計測対象 5 パネルの p95 は 20 ms を超えない** — 3D 散布図の描画面積は現行の約 469×438 px から約 589×661 px へ増え(§6.1)、点の半径も `min(width, height)` 比で大きくなる。点の数は変わらないため塗りの面積の増加だけが負荷の増分である。— 検証方法: Requirement 7.1 / 状態: 未検証。超えた場合は roadmap §2「未確定」に従い、この unit の中で問いを立てる(削る候補は 3D 散布図の枠の大きさ)
3. **ログストリームの折り返しは現行より悪化しない** — 案 D のログストリームの枠幅は表示領域の 12 分の 4 で、現行の 3 列均等(3 分の 1)と同じ幅になる(§6.4)。— 検証方法: Requirement 5.2・5.3 / 状態: 計算上は検証済み、実機は未検証
4. **`panels` の型不一致は `wails build` の失敗として現れる** — `wails.json` の `frontend:build` が `npm run build`(`next build`)を回し、`next build` は型検査を含む。`npm run lint`(Biome)は型検査をしないため、型の契約(§5.1)の検証は `wails build` が担う。— 検証方法: Requirement 3.3 / 状態: 未検証
5. **Tailwind CSS 4 の組み込みユーティリティで 12 列 × 8 行の格子と領域の指定を表せる** — `grid-cols-12`・`grid-rows-8` は組み込みで、領域名の指定は任意プロパティ記法で書ける。— 検証方法: `npm run build` が通り、Requirement 1.1・1.2 を満たすこと / 状態: 未検証

## 4. 用語定義

| 用語 | 定義 |
| ---- | ---- |
| 格子(grid) | 表示領域を 12 列 × 8 行に等分したトラックの集合。`DashboardGrid` が敷く |
| 領域(area) | 格子の中で 1 つの枠が占める矩形。列と行の開始位置と本数で定める |
| slot | 6 枠それぞれの役割名(`timeseries`・`gauge`・`log`・`scatter`・`depgraph`・`commit`)。領域名と `panels` の鍵に使う。計測器のパネル名(`PANEL_NAME`)と同じ語を使い、ログストリームだけは計測対象外のため `log` を新たに置く |
| 枠(Panel) | 1 つの領域を占める `section`。枠線と背景を持ち、見出しを持たない |
| 帯 | 横に長い枠。本書では上段の折れ線グラフの枠を指す |
| 中央主役型 | 中央に最も大きい 1 枠を置き、上に帯、周囲に補助の枠を置く配置の型(`research.md` §1.2) |

プロジェクトは用語集(`docs/glossary.md`)を持たないため、上記は本書で定義し、既存コードの語彙(`PANEL_NAME`・`Panel`・`DashboardGrid`)に合わせている。

## 5. 公開インターフェース(API)

3 つとも TypeScript のコンポーネントで、いずれも Server Component のまま(状態もイベントハンドラも持たない)。ファイルの配置は本書では定めない(dev-decompose の責務)。

### 5.1. `DashboardGrid`

6 枠の配置を決める器。子要素ではなく、slot を鍵にした本文の record を受け取る。

- **定義**:

```tsx
export type DashboardSlot = 'timeseries' | 'gauge' | 'log' | 'scatter' | 'depgraph' | 'commit';

export type DashboardGridProps = {
  // 各 slot に置くパネルの本文。値を ReactElement に限るのは、null・文字列・配列を
  // 型の段階で排除し、6 枠すべてに要素が入ることを保証するためである。
  panels: Readonly<Record<DashboardSlot, React.ReactElement>>;
};

export function DashboardGrid(props: DashboardGridProps): React.JSX.Element;
```

- **入力 / 出力**: 入力は 6 つの slot をすべて鍵に持つ record。出力は 1 個の格子コンテナと、その直下の 6 個の `Panel`。
- **事前条件**: `panels` が 6 つの slot をすべて持ち、余分な鍵を持たない。これは型が強制し、違反は `next build`(`wails build` が回す)の型検査で失敗する(§3 前提 4)。実行時の検査は持たない。
- **事後条件**: (1) §6.1 の格子(12 列 × 8 行、全トラック `minmax(0, 1fr)`、隙間 8 px、外周余白 8 px)を表示領域の幅・高さいっぱいに敷く。(2) 各 slot の本文を、その slot の `Panel` で包んで §6.1 の領域に置く。(3) 6 個の `Panel` の DOM 順は §6.1 の「順」列のとおり。(4) ページ全体にスクロールバーを出さない(格子は `overflow: hidden`)。
- **エラー**: 無し。型で表現不能化しているため、実行時に失敗する経路を持たない。
- **置き換える凍結済みの契約**: `docs/specs/001-dashboard-mvp/001-dashboard-shell/spec.md` §5.7 の「`children` はちょうど 6 個の `Panel`」と「6 個でない場合に `console.error` を出す」(同 Requirement 1.4)を本契約で置き換える。個数の誤りが型で防がれるため、実行時の検査と、それを描画中に 1 回だけ出すための制約(`'use client'` を `page.tsx` へ広げない理由。コミット `5fa2a60`)は不要になる。同 Requirement 1.1(3 列 × 2 行)と 1.2(見出し文字列の表示)も置き換える。同 Requirement 8.3〜8.5(リサイズ追随・ページのスクロール禁止・枠内スクロール)は本書 Requirement 1・2 が引き継ぐ。

### 5.2. `Panel`

1 つの領域を占める枠。見出しを持たない。

- **定義**:

```tsx
export type PanelProps = {
  slot: DashboardSlot;        // 占める領域。§6.1 の領域名と一致する
  children: React.ReactNode;  // 本文
};

export function Panel(props: PanelProps): React.JSX.Element;
```

- **入力 / 出力**: 出力は `section` 1 個。その中に本文領域(`div`)1 個を置く。
- **事前条件**: `DashboardGrid` が敷く格子の直下でのみ使う(領域名が格子の定義に依存するため)。同じ `slot` の `Panel` を 1 つの格子に 2 個置かない(`DashboardGrid` が record の鍵ごとに 1 個ずつ生成するので、`page.tsx` からは破れない)。
- **事後条件**: (1) `section` の `grid-area` が `slot` の値と一致する。(2) `section` は枠線 `--color-border`(1 px)・背景 `--color-surface-1`・角丸を持つ。(3) `section` の中に `h2` と区切り線を描かない。(4) 本文領域の内側余白は左右 12 px・上下 8 px(現行と同じ)。(5) 本文が枠の高さを超えたとき、本文領域の内側だけが縦にスクロールし、`section` の外へはみ出さない。
- **エラー**: 無し。
- **置き換える凍結済みの契約**: `001-dashboard-shell/spec.md` §5.7 の `PanelProps.title` と「6 枠の見出し文字列」の表を廃止する。見出し文字列(`Log Stream` 等)は画面に出さなくなるが、README「画面」表の「パネル」列の日本語名は残る(§6.3)。

### 5.3. `Home`(`frontend/src/app/page.tsx` の既定エクスポート)

画面の組み立て。

- **定義**: `export default function Home(): React.JSX.Element;`(変更なし)
- **事後条件**: `DashboardGrid` を 1 個描き、`panels` に §6.2 の対応で 6 パネルのコンポーネント要素を渡す。見出し文字列の定数(現行の `PANEL_TITLES` 等)と、題名から本文を選ぶ分岐(現行の `panelBody`)を持たない。配置の数値(列・行)を持たない(§6.1 のロジックの所在)。
- **エラー**: 無し。

## 6. データ構造

### 6.1. 格子と 6 枠の配置(案 D)

格子は 12 列 × 8 行。全トラックは `minmax(0, 1fr)`(中身がトラックを押し広げない)。トラック間の隙間は 8 px、格子の外周余白は 8 px。高さは表示領域(`100dvh`)、幅は 100%。

`research.md` §2 案 D は 12 列 × 16 行で書かれているが、行の値(4・12・6・6)はすべて 2 で割り切れるため、8 行にしても各枠の幾何は変わらない。8 行にするのは Tailwind CSS 4 の組み込みユーティリティ(`grid-rows-8`)で書けるためである(16 行は任意値の記法が要る)。列は 10・2・4・5・3 で 12 のまま。

| 順 | slot | 領域名 | 列(開始 / 本数) | 行(開始 / 本数) | 位置(README「位置」列の語) |
| :- | :- | :- | :- | :- | :- |
| 1 | `timeseries` | `timeseries` | 1 / 10 | 1 / 2 | 上の帯 |
| 2 | `gauge` | `gauge` | 11 / 2 | 1 / 2 | 右上 |
| 3 | `log` | `log` | 1 / 4 | 3 / 6 | 左の縦長 |
| 4 | `scatter` | `scatter` | 5 / 5 | 3 / 6 | 中央(最も大きい枠) |
| 5 | `depgraph` | `depgraph` | 10 / 3 | 3 / 3 | 右の上段 |
| 6 | `commit` | `commit` | 10 / 3 | 6 / 3 | 右の下段 |

- 列・行の開始は 1 始まり(CSS のグリッド線の番号)。
- 「順」は DOM 順であり、領域の左上のセルを上から下、同じ行なら左から右に並べた順である。README「画面」表の行の並びもこの順とする(§6.3)。
- **不変条件**: (a) 6 領域は互いに重ならず、96 セル(12 × 8)を余さず埋める(20 + 4 + 24 + 30 + 9 + 9 = 96)。(b) `scatter` の面積(30 セル)は `depgraph`(9 セル)より大きい(`research.md` §3 論点 5 の回答)。(c) `log` の幅は 12 分の 4 で、現行の 3 列均等(3 分の 1)と等しい(§6.4)。
- **ロジックの所在**: 格子の定義(列数・行数・隙間・余白)は `DashboardGrid` に、slot から領域名への対応は `Panel` に置く。`page.tsx` は slot と本文の対応(§6.2)だけを持ち、配置の数値を持たない。配置を変えるときは本表と `DashboardGrid`・`Panel` だけを変える。

各枠の大きさの概算(隙間と余白を引いた値。枠線を含む)。人間が目視と Web インスペクタで配置を照合するときの基準に使う。

| slot | 1440 × 900(起動時) | 1100 × 720(下限) |
| :- | :- | :- |
| `timeseries` | 1185 × 215 | 902 × 170 |
| `gauge` | 231 × 215 | 174 × 170 |
| `log` | 469 × 661 | 356 × 526 |
| `scatter` | 589 × 661 | 447 × 526 |
| `depgraph` | 350 × 327 | 265 × 259 |
| `commit` | 350 × 327 | 265 × 259 |

計算: 1 列 = (幅 − 16 − 8 × 11) ÷ 12、1 行 = (高さ − 16 − 8 × 7) ÷ 8。枠の幅 = 列幅 × 本数 + 8 × (本数 − 1)。高さも同様。小数は四捨五入した。

### 6.2. slot とパネルの対応

| slot | 本文のコンポーネント | README「画面」表の「パネル」 | 計測器の `PANEL_NAME` |
| :- | :- | :- | :- |
| `timeseries` | `TimeseriesPanel` | 折れ線グラフ | `timeseries` |
| `gauge` | `GaugePanel` | タコメータ | `gauge` |
| `log` | `LogStreamPanel` | ログストリーム | (計測対象外) |
| `scatter` | `Scatter3DPanel` | 3D 散布図 | `scatter` |
| `depgraph` | `DependencyGraphPanel` | グラフビュー | `depgraph` |
| `commit` | `CommitGraphPanel` | コミットグラフ | `commit` |

6 つのコンポーネントと Go の生成源 5 本(`logsource.go`・`commitsource.go`・`graphsource.go`・`scattersource.go`・`metricsource.go`)は本 unit で変更しない(Requirement 4.2)。

### 6.3. README「画面」節の形式

- 冒頭の 1 文で配置の型を述べる。「中央に 3D 散布図を置き、上に折れ線グラフの帯、左にログストリームの縦長、右上にタコメータ、右にグラフビューとコミットグラフを積む中央主役型で、6 枠は均等でなく、見出しを持たない」の趣旨を 1 文で書く。「3 列 2 行」「枠の題名」の語を含めない。
- 表の列は「パネル」「位置」「内容」の 3 列。「枠の題名」列を持たない。
- 表の行は 6 行で、並びは §6.1 の「順」、「位置」の値は §6.1 の「位置」列の語、「パネル」の値は §6.2 の「パネル」列の語とする。「内容」列は現行の文を保つ。
- 表の下の「並び順は画面の配置(1 行目 左→右、2 行目 左→右)と一致する」は、「表の並びは配置の順(上から下、同じ高さでは左から右)」の趣旨の 1 文に置き換える。
- ASCII 図は載せない。

### 6.4. ログストリームの本文幅(事実の記録)

ログストリームの 1 行は固定幅の 3 列(時刻 80 px・ツール 64 px・レベル 48 px)と、残りを使う本文列から成り、列間の隙間は 8 px × 3、枠の本文余白は左右 12 px、枠線は 1 px × 2(`LogStreamPanel.tsx` `renderLine`・§5.2)。本文列の幅 = 枠幅 − 2 − 24 − 192 − 24 = 枠幅 − 242。

| ウィンドウ | 現行(3 列均等)の枠幅 | 案 D の枠幅 | 本文列の幅 |
| :- | :- | :- | :- |
| 1440 × 900 | 469 | 469 | 227 |
| 1100 × 720 | 356 | 356 | 114 |

擬似ログの本文は 30〜55 文字(`logsource.go`)で、12 px の等幅書体では 1 文字が約 7 px なので、1440 × 900 では多くの行が 2 行に、下限では 3〜4 行に折り返す。これは現行と同じであり、案 D で悪化しない。本文幅の下限は「現行と同値」を契約とし(Requirement 5)、折り返し規則(`break-all`)と列構成は変えない(§2 対象外)。折り返しを減らす改善(ツール列を落とす・本文を短くする等)は roadmap §3 の「4 パネルの中身の作り込み」に当たるため本 unit では扱わず、§8 に論点として残す。

## 7. 振る舞い(受け入れ基準)

### Requirement 1: 格子と 6 枠の配置

**対象**: §5.1 `DashboardGrid` / §6.1 格子と配置

**受け入れ基準**:
1.1. システムは、表示領域の幅・高さいっぱいに 12 列 × 8 行の格子を敷き、全トラックを `minmax(0, 1fr)`、隙間を 8 px、外周余白を 8 px としなければならない。(常時)
1.2. システムは、6 枠を §6.1 の表が定める列・行の領域に配置しなければならない。(常時)
1.3. システムは、6 枠の DOM 順を §6.1 の「順」列(`timeseries`・`gauge`・`log`・`scatter`・`depgraph`・`commit`)としなければならない。(常時)
1.4. ウィンドウの大きさが変わったとき、システムは格子を表示領域全体に追随させ、各枠の幅・高さを §6.1 の列・行の本数の比で縮小・拡大しなければならない。(イベント)
1.5. ウィンドウが下限(幅 1100 px・高さ 720 px)の大きさにある間、システムは 1440 × 900 と同じ格子と領域で 6 枠を配置し、配置を切り替えてはならない。(状態)
1.6. システムは、ページ全体に縦方向・横方向のスクロールバーを発生させてはならない。(常時)
1.7. ウィンドウが 1440 × 900 のとき、システムは各枠の幅・高さを §6.1 の概算表の値から ±4 px 以内にしなければならない。(イベント)

### Requirement 2: 見出しを持たない枠

**対象**: §5.2 `Panel`

**受け入れ基準**:
2.1. システムは、画面の DOM に `h2` 要素を 1 個も持たず、6 枠のいずれにも見出し行と区切り線を描いてはならない。(常時)
2.2. システムは、各枠に枠線 `--color-border`(1 px)と背景 `--color-surface-1` を適用し、格子の背景(`--color-surface-0`)との差で枠の境界を示さなければならない。(常時)
2.3. システムは、各枠の `grid-area` を、その枠の `slot` の値と一致させなければならない。(常時)

## 8. 実現方針

- **`children` ではなく slot の record で受ける**: 6 枠を子要素の順序で置くと、順序の誤りが実行時にしか分からず、個数の検査(`console.error`)も残る。`Record<DashboardSlot, ReactElement>` で受ければ、欠落・重複・順序の誤りを型検査で潰せ(§3 前提 4)、実行時の検査と、それを描画中に 1 回だけ出すための制約(`'use client'` を `page.tsx` へ広げない。コミット `5fa2a60`)が消える。`DashboardGrid` と `Panel` は Server Component のまま変えない(状態を持たないため `'use client'` は要らない)。
- **領域の指定は `Panel` 側に置く**: `grid-area` は格子の直下の要素(`section`)に付く必要がある。`DashboardGrid` が子要素へクラスを注入する(`cloneElement`)より、`Panel` が `slot` から領域名を引くほうが単純で、対応表が 1 箇所(`Panel`)に閉じる。Tailwind が原文からクラス名を拾うため、slot ごとのクラス名は文字列連結でなく静的な対応表(`Record<DashboardSlot, string>`)で持つ(`LogStreamPanel.tsx` の `LEVEL_CLASS` と同じ理由)。
- **格子は 12 列 × 8 行**: 案 D の 12 列 × 16 行と同じ幾何(§6.1)。組み込みユーティリティで書けることを優先した。
- **引き継ぐ既存の判断**(git 履歴で確認): 高さを `h-dvh` で取る(`html`・`body` に高さが無いと `h-full` が解決できない。コミット `df59c57`)、格子を `overflow-hidden` で切る(1 px のはみ出しでページにスクロールバーが出る。同)、`section` と本文領域の両方に `min-h-0` を置く(flex 項目の既定 `min-height: auto` が中身で枠を押し広げる。コミット `e185307`)。これらは Requirement 1.6・2.5 として残す。
- **ログストリームの本文幅は「現行と同値」を契約にする**(§6.4・Requirement 5): 案 D の枠幅が現行と等しいため、配置の変更として扱える範囲では悪化も改善も無い。改善するには `LogStreamPanel` の列構成か折り返し規則に手を入れる必要があり、roadmap §3 の対象外に当たる。この判断はユーザーの追加指示(「中身に手を入れる必要があるなら、roadmap §3 のスコープ外に当たるかを判断し、当たるなら spec には入れず論点として報告する」)に従う。改善の候補(ツール列を落とす、本文を短くする、下限の枠幅で折り返しを避ける本文長にする)は別の依頼の論点として残す。
- **凍結済み文書との関係**: `001-dashboard-shell/spec.md` §5.7・Requirement 1.1・1.2・1.4 を §5.1・§5.2 で置き換える。`004-metrics-panels/spec.md` Requirement 11.4(README「画面」表と実画面の 1 対 1 対応)は Requirement 6.4 が引き継ぐ。凍結済み文書は編集しない。
- **`h2` を消した後の見出しの行方**: 画面には出さない。パネルの識別は README「画面」表の「パネル」列と「位置」列で行う(request.md §5 決定 3)。

# depgraph-density — 仕様

## 1. 目的と背景

roadmap `002-visual-refinement` の unit #5(最終 unit)。依存グラフ(Dependency Graph)パネルのノード数を増やし、円周上の等角配置をやめて疎密のある配置にする(request.md §2.3、roadmap §1 の #5)。

依存グラフの土台は凍結済み unit `001-dashboard-mvp/003-graph-panels`(以下「凍結 spec」)が作った。凍結 spec の**前提 3(ノード数 10 で固定)と前提 4(円環上の錨からのドリフトで配置し力学モデルを持たない)を、本 spec の §3 前提 1・前提 2 で置き換える**。凍結 spec の他の部分(`GraphNode`・`GraphEdge`・`DependencyGraph` の型と不変条件、`graphSource` の公開インターフェース、フロントエンドの購読・補間・配置関数の契約、コミットグラフに関する全記述)は変更せず、そのまま有効とする。本 spec はコミットグラフ(`CommitGraphPanel`・`commitSource`)に触れない。

参考は Obsidian のグラフビューが出す見え方(§9 参考資料)。密な塊と疎な周辺、リンクの多いノードが大きく中央寄りに見える類のものであり、力学(force-directed)モデルの実装そのものではなく、その「見え方」を目標にする。

## 2. スコープ

### 対象(やること)

- `graphsource.go` の書き換え: ノード数を 10 から 36 へ増やす。円周上の等角配置(`graphAnchorRadius` の単一円)をやめ、クラスタ(疎密の塊)ベースの錨配置に変える。
- `graphNodeIDs` を 36 個の英語のサービス名へ拡張する。
- 基幹エッジ・揺らぎエッジの生成規則をクラスタ構造に合わせて作り直す(§6.6)。
- `DependencyGraphPanel.tsx` の `drawNodes` を、健康状態(`Health`)で束ねて描く形に変える(`fillStyle` の切り替え回数をノード数によらず高々 3 回に抑える。§3 前提 5)。
- `graphsource_test.go` へ、ノード数が 10 より多いことと、配置が等角・等距離でないことを検証するテストを追加する。
- ノード数・エッジ数の変化に対する p95 の実測(着手時・完了時)。
- `lib/depgraph.ts` の `RADIUS_BASE_RATIO` / `RADIUS_LOAD_RATIO`(円の半径を決める比率定数。`Load` の重み付けそのものは変えない)を、ノード数 36 のもとで密なクラスタ(hub、14 ノード)の円どうしが個々に見分けられなくなるほど重なるなら、値を小さくして調整してよい(§7 Requirement 8)。`placeNode` の関数シグネチャ・引数・返り値の型は変えない(§5.3)。

### 対象外(やらないこと)

- **力学モデル(反発 + バネなどの force-directed layout)の実装** — 理由: 凍結 spec §3 前提 4 の「反復計算とパラメータ調整を要し、擬似データを見せるという目的に対して複雑すぎる」という判断は、ノード数を増やしてもなお成り立つ。`CLAUDE.md`「過度な抽象化を避ける」。クラスタの種と最小距離の制約による静的な配置(§3 前提 2)で疎密の見え方を作る。
- **`GraphNode` / `GraphEdge` / `DependencyGraph` の型・フィールドの変更** — 理由: フロントエンドの描画は既にノード・エッジの配列を汎用的に走査する作りであり(`DependencyGraphPanel.tsx`)、ノード数を増やすだけなら公開インターフェース(凍結 spec §5.2・§6.3〜§6.5)を変えずに済む。契約変更は不要な複雑化になる。
- **マウス操作(ノードの選択・移動・ズーム)** — 理由: roadmap のスコープ外(request.md §4)。
- **コミットグラフ・ログストリーム・折れ線グラフ・タコメータへの変更** — 理由: 本 unit の範囲は依存グラフに閉じる(roadmap §1 の依存関係の記述)。
- **可視化ライブラリ(d3・cytoscape・vis-network 等)の導入** — 理由: 凍結 spec §3 前提 5 の判断を維持する。Canvas 2D の自前描画のままノード数を増やす。
- **ノードの `Load`(円の大きさ)の意味を次数(リンク数)へ変える** — 理由: `Load` は既存の「サービス負荷」を表す値であり、疎密の見た目は錨の配置(中心からの距離)で作る(§3 前提 3)。2 つの独立した概念(負荷・次数)を 1 つの値へ混ぜると、どちらの変化も読み取りにくくなる。
- **`palette.ts`(unit #3 が導入した連続カラーマップ)の依存グラフへの適用** — 理由: 依存グラフのノードは `ok` / `warn` / `down` という離散的な健康状態を表し、連続的な値(高さ等)を持たない。`palette.ts` は 3D 散布図の連続値の着色のために作られたものであり、離散状態には既存の 3 色のトークンの使い分けで足りる(§3 前提 6)。
- **ラベルの重なり対策(間引き・非表示・自動配置)** — 理由: `DependencyGraphPanel.tsx` の `drawLabels` は既存どおり全ノードのラベルを毎フレーム描く(凍結 spec 由来の既存動作を維持する)。ノード数が増えると密なクラスタでラベルが重なって読みにくくなるが、これは request.md §2.3・roadmap §1.1 が求める「密な塊と疎な塊の見分けやすさ」(ノードの配置の見た目)とは別の懸念であり、本 unit の範囲(依存グラフの**配置**の変更)には含めない。円どうしの重なりは§7 Requirement 8 の目視で許容範囲を判断する。

## 3. 前提(未検証の賭け)

1. **依存グラフのノード数を 36 個に増やす。** — 10 個の 3.6 倍。Obsidian のグラフビューが「密な塊と疎な周辺」に見えるのは数十〜数百ノードの規模であり(§9 参考資料)、10 個では疎密を作っても塊として視認しづらい。一方で `arc` の呼び出し回数がそのまま増える(unit #4 からの申し送り)。呼び出し回数の増加自体は unit #3(点を 23 倍)で許容範囲だったが、依存グラフは現在ノードごとに `ctx.fillStyle` を切り替えており、これは切り替え回数がノード数に比例して増える点で unit #3 と条件が異なる。この対策を前提 5 に置く。検証方法: Requirement 1 のテストと p95 の計測 / 状態: テストで検証する。
2. **ノードの配置は、少数のクラスタ(疎密の塊)を Go 側で 1 度だけ算出し、各ノードをクラスタ中心からのオフセットへ静的に割り当てる。毎フレームの反復・力学シミュレーションは行わない。** — `newGraphSource` の初期化時に 1 回だけクラスタ中心とノードごとのオフセットを計算し(§6.6)、以後は既存の `drift` / `clampUnit` による錨からの微小なドリフトだけを毎フレーム行う(凍結 spec §6.6 の仕組みをそのまま流用)。これにより「毎フレームの反復を Go 側でどう抑えるか」という論点を、初期化時の 1 回限りの計算に落とす。クラスタ内のオフセットは乱数 + 最小距離の制約(ローカルハブを除く同一クラスタ内の 2 点が近すぎれば再抽選、最大 20 回試行して超えたら諦めて採用する)で決め、力学モデルの反復とは異なり試行回数の上限を持つ。ローカルハブ(オフセット半径 0、§6.6 手順 3)は定義上クラスタ中心そのものであり、rank 1 のノードとの距離はオフセット半径の値で決定的に定まる(角度を引き直しても変わらない)ため、最小距離の制約の対象から外す(ハブに最も近いノードが最小距離未満になりうることは、ハブを中心に置くという配置方針そのものが持つ帰結であり、乱数由来の偶発的な密集ではない)。検証方法: Requirement 2 のテストとコードレビュー(初期化時にしか呼ばれない関数であることの静的検査) / 状態: テストで検証する。
3. **疎密は「クラスタの配置」(中心に近い密なクラスタと、周辺に離れた疎なクラスタ)で作り、個々のノードの次数(リンク数)は錨のクラスタ内オフセット(中心寄りか周辺寄りか)にだけ影響させ、円の大きさ(`Load`)には影響させない。** — §2 対象外の理由と同じ。次数はエッジ構造(§6.6)から静的に定まる「構造上の次数」(初期化時に基幹エッジだけから数える。揺らぎエッジの増減では変えない)を使う。次数が高いノードほどクラスタ中心に近いオフセットを割り当てる(Obsidian のグラフビューでリンクの多いノードが中央寄りに見える性質を模す)。検証方法: 目視 / 状態: 未検証。
4. **エッジは、クラスタ内の星形(スポーク)接続とクラスタ間の背骨(バックボーン)接続からなる基幹エッジ(36 ノードの全域木、35 本、常に連結を保つ)と、これに追加する揺らぎエッジ(候補 36 本、確率で付け外し)の 2 層を維持する。** — 凍結 spec §6.6 の「基幹エッジ + 揺らぎエッジ」の 2 層構成を踏襲し、ノード数が増えても連結性を構造(全域木)で保証する。エッジの総数は最大 35 + 36 = 71 本で、`ctx.strokeStyle` を 1 度だけ設定してから全エッジを描く既存の描画順(凍結 spec §8)は変えないため、エッジ数の増加は `fillStyle` 切り替えの対象にならない。検証方法: Requirement 2・4 のテスト / 状態: テストで検証する。
5. **`DependencyGraphPanel.tsx` の `drawNodes` は、ノードを `Health` の値(`ok` / `warn` / `down`)で 3 群にまとめ、群ごとに `ctx.fillStyle` を 1 度だけ設定してから群内の全ノードを描く。** — 現状は 1 ノードごとに `fillStyle` を設定しており、ノード数が 10 から 36 に増えると切り替え回数もそのまま 3.6 倍になる。unit #3・#4 からの申し送り(「`fillStyle` の切り替え回数を増やさなければ p95・max は悪化しない」)に従い、切り替え回数をノード数によらず高々 3 回(ok・warn・down のうち実在する群の数)に抑える。描画順序(エッジが先、ノードが後)と輪郭線の描画は変えない。健康状態ごとにノードを分けても、円を描く `ctx.arc` の呼び出し回数自体は変わらない(36 回)。検証方法: p95 の計測と静的検査(ループ構造の確認) / 状態: 未検証(p95 は着手時・完了時の実測で確認する)。
6. **乱数は既存どおり `math/rand`(v1)を使う。** — 凍結 spec §3 前提 8 と同じ理由(`math/rand/v2` は `wails build` のバインディング生成で失敗する)。検証方法: `wails build` の成功 / 状態: 既存 unit で検証済み。

## 4. 用語定義

凍結 spec §4 の用語(レーン・先端・分岐・マージ・モデル座標・補間)はコミットグラフに関するものを含め、そのまま有効とする。本 spec で追加する用語は次のとおり。

| 用語 | 定義 |
| ---- | ---- |
| クラスタ(cluster) | ノードの錨をまとめる塊。中心からの距離と塊の広がり(スプレッド)を持つ |
| クラスタ中心(cluster center) | クラスタに属するノードの錨が散らばる基準点。モデル座標で表す |
| スプレッド(spread) | クラスタ中心からノードの錨がどれだけ散らばりうるかを表す半径 |
| 構造上の次数(structural degree) | 基幹エッジだけを数えたノードの接続本数。揺らぎエッジの増減では変わらない |
| ローカルハブ(local hub) | クラスタ内で他の全ノードのスポークを受ける 1 ノード(クラスタ内で構造上の次数が最大) |
| バックボーン(backbone) | 各クラスタのローカルハブどうしを結び、グラフ全体を連結に保つ基幹エッジの部分集合 |

## 6. データ構造

### 6.1〜6.5. `Commit` / `GraphNode` / `GraphEdge` / `DependencyGraph`(変更なし)

凍結 spec §6.1〜§6.5 のとおり。フィールド・不変条件・生成関数を変更しない。

### 6.6. `graphSource` の内部状態(非公開・変更)

- `graphNodeCount = 36`(旧: 10)。
- `graphClusterCount = 4`。クラスタごとに次を定数として持つ:

  | クラスタ | ノード数 | 中心の極座標(半径, 角度) | スプレッド半径 |
  | :--- | ---: | :--- | ---: |
  | 0(hub、密) | 14 | (0.10, 0°) | 0.32 |
  | 1 | 8 | (0.55, 150°) | 0.16 |
  | 2 | 7 | (0.68, 260°) | 0.14 |
  | 3 | 7 | (0.82, 40°) | 0.12 |

  中心の角度を等間隔(90° 刻みなど)にしないのは、クラスタの並び自体を等角配置にすると本 unit が解消しようとしている見た目が塊の単位で再現されてしまうため。半径とスプレッドをクラスタごとに変えるのは、中心に近い密なクラスタと周辺の疎なクラスタを作るため(§3 前提 1)。ノード数の内訳(14, 8, 7, 7、合計 36)は hub クラスタを最も密にし、残りを周辺へ振り分ける。

- **錨の算出(`newGraphSource` 内で 1 度だけ)**:
  1. 各クラスタに割り当てるノードの基幹エッジ構造(スポーク + バックボーン、下記)を先に確定し、ノードごとの構造上の次数を数える。
  2. クラスタごとに、所属ノードを構造上の次数の降順に並べる。
  3. 並べた順に、クラスタ中心からのオフセット半径を `spread * rank / (count - 1)`(`rank` は 0 始まりの順位)で割り当てる。次数が高い(`rank` が小さい)ノードほどオフセット半径が小さく、クラスタ中心に近い錨を持つ。
  4. オフセットの角度は `rnd` から一様に選ぶ。ただし**ローカルハブ(オフセット半径 0)を除く**同一クラスタ内の既に確定した錨との距離が `graphMinNodeDistance`(0.05)未満なら、最大 20 回まで角度を引き直す。20 回を超えたらそのまま採用する(反復に上限を持つ。§3 前提 2)。ハブとの距離は最小距離の判定に含めない(§3 前提 2 の注記のとおり、ハブがクラスタ中心にある設計そのものの帰結であり、角度の引き直しでは解消できないため)。
  5. 得られた錨座標を `clampUnit` で単位正方形へ切り詰める。
- 錨の算出後は、凍結 spec §6.6 と同じく各ノードを錨へ引き戻しつつ小さな乱歩を加える(`drift` / `clampUnit`。`graphNodePull` / `graphNodeJitter` は値を変えない)。`Load` の扱い(`graphLoadPull` 等)も変えない。
- `Health` の遷移規則(`graphHealthChance` / `nextHealth`)は変えない。
- **エッジの生成規則**:
  - **クラスタ内スポーク(基幹)**: クラスタごとに、構造上の次数を数える前提として「先頭ノード(配列内の添字 0)」をローカルハブとし、同クラスタの他の全ノードからローカルハブへ 1 本ずつ張る。4 クラスタで `(14-1)+(8-1)+(7-1)+(7-1) = 32` 本。
  - **バックボーン(基幹)**: クラスタ 1・2・3 のローカルハブから、クラスタ 0(hub)のローカルハブへ 1 本ずつ張る。3 本。
  - 基幹エッジは合計 35 本(ノード数 36 に対する全域木で、グラフ全体が常に連結)。凍結 spec §6.6 の「基幹エッジはつねに存在する」性質を維持する。
  - **揺らぎエッジ(候補)**: 基幹エッジと重複しない組を `graphOptionalEdgeCount = 36` 本用意する(クラスタ内の非隣接ペアとクラスタ間のペアを混在させ、`rnd` で重複なく選ぶ)。凍結 spec §6.6 と同じく確率(`graphEdgeToggleChance`)で付け外しし、半数ほどを初期状態で活性にする。
  - エッジの総数は最大 `35 + 36 = 71` 本(旧: 最大 20 本)。
- `graphNodeIDs` は 36 個の英語のサービス名の配列(既存の 10 個を含む)。並びがクラスタと錨の割り当て順を決める(既存の `graphCoreEdges` / `graphOptionalEdges` の役割を、クラスタ内の添字ベースの生成規則へ置き換える)。

### 6.7. `DashboardSnapshot`(変更なし)

凍結 spec §6.7 のとおり。`Graph.Nodes` の長さが 36 になる点を除き変更しない。

### 6.8. デザイントークン(変更なし)

凍結 spec §6.8 のとおり。新しいトークンは追加しない(§2 対象外)。

## 7. 振る舞い(受け入れ基準)

凍結 spec の次の受け入れ基準も、本 spec が明示的に置き換える箇所(4.3・10.5・12.3・12.4)を除き、変更なく有効とする(ノード数・エッジ数上限が 36・71 になった前提のもとで適用する)。

- Requirement 4(`graphSource` の契約)のうち 4.1・4.2・4.4・4.5・4.6(4.3 は本 spec Requirement 1.1・1.3 が置き換える)。
- Requirement 10(依存グラフの描画と補間)のうち 10.1・10.2・10.3・10.4・10.6・10.7・10.8・10.9(10.5 は色の決め方自体は変えないが、本 spec Requirement 6 が `fillStyle` の切り替え回数の制約を追加する)。
- Requirement 12(検証手段の成立)のうち 12.1・12.2(12.3・12.4 は本 spec Requirement 7.1・7.3 が置き換える)。

以下は本 unit で追加・変更する受け入れ基準。

### Requirement 1: ノード数の変更

**対象**: §6.6 内部状態

**受け入れ基準**:
1.1. システムは、`graphSource.Next()` が返す `DependencyGraph.Nodes` の長さをつねに `graphNodeCount`(36)にしなければならない。(常時。凍結 spec 4.3 を置き換え)
1.2. システムは、`graphNodeIDs` の要素数を `graphNodeCount` と一致させなければならない。(常時)
1.3. `Snapshot` が `startup` の後に呼ばれたとき、システムは `Graph.Nodes` の長さを 36 にしなければならない。(イベント。凍結 spec 7.4 を置き換え)

### Requirement 2: 配置の疎密(等角・等距離でないこと)

**対象**: §3 前提 1・2・3 / §6.6 錨の算出

**受け入れ基準**:
2.1. `newGraphSource` が返す初期状態について、システムは全ノードの錨を原点を中心とした極座標の角度でソートしたとき、隣り合う角度差(360° をまたぐ組を含む)の最大値と最小値の差が 5° を超える状態にしなければならない(角度間隔が一様でない)。(常時)
2.2. `newGraphSource` が返す初期状態について、システムは全ノードの錨の原点からの距離の標本標準偏差を 0.05 より大きくしなければならない(距離が一様でない)。(常時)
2.3. `newGraphSource` が返す初期状態について、システムは少なくとも 1 組のノードの錨間の距離を 0.2 未満に(密な塊)、少なくとも 1 組を 0.9 より大きく(疎な塊)しなければならない。(常時)
2.4. `Next` を 1000 回連続で呼び出す間、システムは各ノードの座標(`X`・`Y`)を、そのノードの初期状態(`newGraphSource` 直後の `Snapshot()`)の座標から、`graphNodePull` と `graphNodeJitter` の値だけから定まる最大変位(ドリフトが 1 呼び出しあたりに動かせる距離の上限)の合計を超えて動かしてはならない(公開出力だけで観測できる形での、錨の飛躍(再算出)が無いことの確認。状態)。加えて、§6.6 の錨の算出(クラスタ中心・スプレッド・構造上の次数に基づく計算)を行う関数が `newGraphSource` の初期化コードからのみ呼ばれ、`Next` の呼び出し経路には無いことを、コードレビュー(静的検査)で別途確認する(この静的検査は振る舞いテストを補うものであり、単独では 2.4 の合格根拠にしない)。
2.5. `newGraphSource` を異なる `rnd` の種で 20 回実行したとき、システムはいずれの実行でも 2.1〜2.3 を満たさなければならない(特定の乱数列にだけ依存しない)。(常時)

## 8. 実現方針

- **配置算出の所在**: 引き続き Go 側(`graphsource.go`)。フロントエンドは §5.3 の配置関数のみを持ち、ノード数の増加やクラスタ構造を一切知らない(roadmap §3 の分担を維持)。
- **クラスタベースの静的配置**: `newGraphSource` の初期化時に、クラスタ中心・スプレッド(§6.6 の表)とエッジ構造(スポーク・バックボーン)を先に確定し、構造上の次数から錨のオフセット半径を決める。この計算は 1 回限りであり、`Next` の呼び出しのたびに繰り返さない。既存の `drift` / `clampUnit`(unit #2 由来)による毎フレームのドリフトはそのまま使う。
- **エッジの生成**: `graphCoreEdges` / `graphOptionalEdges` という手書きの添字ペアの配列(凍結 spec の実装)を、クラスタとローカルハブの構造から導出する形へ書き換える。生成規則自体は `newGraphSource` 内の初期化コードに閉じ、`Next` はこれまでどおり `active` の付け外しと `flow` のドリフトだけを行う。
- **描画側の変更**: `drawNodes` を「`Health` でノードを 3 群に分け、群ごとに `fillStyle` を 1 度設定してから `arc` で描く」形に書き換える。`drawEdges` は既に `strokeStyle` を 1 度だけ設定する形になっており、変更不要。
- **ノード名の拡張**: `graphNodeIDs` を 36 個へ拡張する。既存の 10 個(`api-gateway` 等)を hub クラスタに残し、周辺クラスタには系統だった英語のサービス名(例: `billing`, `email`, `scheduler` 等)を足す。クラスタと ID 配列の対応(どの添字がどのクラスタに属するか)はコードコメントで明示する(実装タスクで確定)。
- **テストの追加**: `graphsource_test.go` に Requirement 2〜4 のテストを追加する。凍結 spec 由来の既存テスト(`graphNodeCount`・`graphNodeIDs`・`graphCoreEdges` を参照するもの)は定数の値が変わるだけで、アサーションの形は変えずに成功する見込み(§3 前提の「既存のアサーションを変えずに成功する」)。ただし `TestGraphSourceBoundedSize` の `maxEdges` 等、定数の再定義に追随が必要な箇所はある。

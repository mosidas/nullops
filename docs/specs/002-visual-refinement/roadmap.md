# visual-refinement — 作業単位への分解

roadmap `001-dashboard-mvp` で動くようになった 6 パネルの画面を、作業中に見えるダッシュボードとして説得力のある見え方にする。配置は見出し無しの不均等な割り付けになり、3D 散布図は軸線を持ちドラッグで視点を変えられ、依存グラフは疎密のあるノード配置になる。これらを macOS の配布ビルド(`wails build`)で人間が目視して承認でき、かつ既存の計測器で計測対象のパネルの p95 が 20 ms 以内であることを確かめられる状態にする。unit の切り方はこの状態から逆算している。

要求の本体は `docs/specs/002-visual-refinement/request.md` にある。本書は要求の内容を再記述せず、章番号で参照する(目的は §1、実装する 3 点は §2、roadmap 全体の完了条件は §3、スコープ外は §4、承認済みの決定は §5、既存コードの事実は §6)。言語規約・コーディング規約は `CLAUDE.md` にある。

## 前提

- 3 点を 1 つの roadmap にまとめて unit へ切り分ける方針、配置案の提示と選択の手順、見出し行の削除、3D 散布図の操作方式は承認済みである(request.md §5)。本書はこれらを再検討しない。
- 既存コードの構造(グリッド・パネル枠・3D 散布図の回転・依存グラフのノード数と配置・計測器・README の画面表)は request.md §6 に 2026-09-06 時点の実物確認済みの事実として列挙されている。各 unit の仕様化はそれを前提にしてよい。
- 6 パネルはそれぞれ独立したコンポーネント(`frontend/src/components/*Panel.tsx`)を持つ。Go 側の生成源は 5 本(`logsource.go`・`commitsource.go`・`graphsource.go`・`scattersource.go`・`metricsource.go`。最後の 1 本が折れ線グラフとタコメータの両方を賄う)。枠の描画は `Panel.tsx`・配置は `DashboardGrid.tsx`・組み立ては `frontend/src/app/page.tsx` が担う。3D 散布図の改修は `Scatter3DPanel.tsx`・`lib/project.ts`・`scattersource.go` に、依存グラフの改修は `DependencyGraphPanel.tsx`・`lib/depgraph.ts`・`graphsource.go` に閉じ、互いに重ならない。
- 計測器 `frontend/src/lib/framestats.ts` はパネル名ごとに n / mean / p95 / max を出す。配布ビルドでコンソールから有効化する口は `window.nullops.enableFrameStats()` であり(`setFrameStatsEnabled` はモジュールの export でコンソールから呼べない。request.md §3・§6 の呼び出し名は実装と一致しないため、本書は実装に合わせる)、起動から p95 を読むまでの手順は凍結済みの `docs/specs/001-dashboard-mvp/005-framestats-runtime/tasks.md` B 節にある(計測には Web インスペクタを開ける `wails build -devtools` のビルドが要る。素の `wails build` ではコンソールを開けず値を読めない。B.2 がその値を配布ビルドの値として扱ってよい根拠を併記している)。計測対象は rAF のループを持つ 5 パネル(`commit`・`depgraph`・`gauge`・`scatter`・`timeseries`)で、ログストリームは DOM の再描画で進みフレーム間隔を持たないため意図的に対象外である(`LogStreamPanel.tsx` 冒頭の注記)。request.md §3 の「全パネルの p95」は本書ではこの 5 パネルと読む。判定の閾値(p95 が 20 ms を超えない)は request.md §3 のとおりで、本 roadmap では計測器を改修しない。
- 依存グラフのノード数 10 と等角配置は凍結済み unit `003-graph-panels` の spec の前提に由来する(request.md §6)。凍結済みの文書は編集せず、前提を置き換える unit の spec に「どの前提を置き換えるか」を明記する。
- 検証は `go vet ./...`・`go test ./...`・`cd frontend && npm ci && npm run lint`・`wails build` と、配布ビルドの人間による目視で行う(request.md §3)。ブラウザ自動化による視覚検証は無い。
- 作業ブランチは `wip/visual-refinement`(request.md §6)。各 unit の作業ブランチはここから派生する。
- 知識 port は無い(`docs/dev/ports/` が存在しない)。
- 外部の参考(request.md §2.2 の参照 URL、§2.3 の Obsidian のグラフビュー、§2.1 の既存ダッシュボード)は各 unit の仕様化で調べる。本書では調べない。

## 1. unit 一覧

| #   | unit                  | 範囲                                                                                                                                                                                   | 依存 |
| :-- | :-------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :--- |
| 1   | `dashboard-layout`    | パネルの見出し行の削除と、6 等分をやめた配置の作り直し(request.md §2.1)。配置案は既存ダッシュボードの調査を経て仕様のゲートで複数提示し、ユーザーが選ぶ。README「画面」表の改訂を含む。 | —    |
| 2   | `scatter3d-controls`  | 3D 散布図の軸線の描画、ポインタのドラッグによるヨー・ピッチの操作と、ドラッグ終了後の自動回転への復帰、点の形の見直し(request.md §2.2)。                                                | 1    |
| 3   | `depgraph-density`    | 依存グラフのノード数の増加と、等角配置をやめた疎密のある配置(request.md §2.3)。凍結済み `003-graph-panels/spec.md` §3 の前提 3(ノード数 10 で固定)と前提 4(円環上の錨からのドリフトで配置し力学モデルを持たない)をこの unit の spec で置き換える。Go 側が生成しフロントエンドが写像する分担は保つ(request.md §4)。                       | 1    |

順序は #1 → #2 → #3 とする。

- #1 を最初に置くのは、3 点のうち人間の決定(配置案の選択)を要する不確実性が最も高く、かつ他の 2 点の見え方を左右するためである。配置が決まらないと 3D 散布図と依存グラフの枠の大きさ(描画面積)が定まらず、軸線の見え方・ノードの疎密の見え方・描画の負荷のいずれも配置後に確かめ直すことになる。加えて、見出し行の削除は全パネルの枠(`Panel.tsx`・`page.tsx`)に触るため、#2・#3 と同時に進めると同じファイルで衝突する。
- #2 を #3 より前に置くのは、3D 散布図が現状で視点を操作する口を持たず(request.md §6)、ポインタ操作・視点の状態・自動回転への復帰という新しい仕組みを WebView 上で成立させる不確実性が、既存の生成と写像の分担を保ったまま配置を変える #3 より高いためである。
- #2 と #3 は依存が #1 のみで、触るファイル群(Go の生成源・フロントエンドのコンポーネントとライブラリ)が重ならないため並行して進めてよい。ただし両方が描画の負荷を増やすため(request.md §3)、後に完了する側の完了条件の計測は、先に完了した側を取り込んだビルドで行う。
- 3 点の統合確認だけの unit は立てない。各 unit が配布ビルドの目視と p95 の計測を完了条件に持ち、後に完了する unit の計測が全体の統合確認を兼ねるため、その中身だけでは仕様化と承認の往復に見合わない。

### 1.1. 各 unit の完了条件

- **`dashboard-layout`**: macOS で `wails build` した配布ビルドを起動すると、6 枠のいずれにも見出し行(`h2` と区切り線)が無く、6 枠が均等でない配置で並び、それが仕様のゲートでユーザーが選んだ配置案と一致する。6 パネルすべてが引き続き更新され続け、30 秒間の観察で停止するパネルが無い。README「画面」節の記述と表が実画面と一致し、表に「枠の題名」列が無い。`wails build -devtools` のビルドで `window.nullops.enableFrameStats()` を呼んで計測し(手順は `005-framestats-runtime/tasks.md` B 節)、計測対象の 5 パネルの p95 がいずれも 20 ms を超えない。`go vet ./...`・`go test ./...`・`cd frontend && npm run lint` がいずれもエラーなく終了する。人間が配布ビルドの画面を目視し、配置の改善を承認する。
- **`scatter3d-controls`**: 配布ビルドの 3D 散布図の枠に軸線が描かれ、放置した状態で自動回転が続く。枠の上でポインタをドラッグするとヨーとピッチが追従して視点が変わり、ドラッグを終えると自動回転へ戻る(30 秒間の観察で回転が再開したまま止まらない)。点の形が仕様で定めた形に変わっている。`wails build -devtools` のビルドで `window.nullops.enableFrameStats()` を呼んで計測し、計測対象の 5 パネルの p95 がいずれも 20 ms を超えない。`go vet ./...`・`go test ./...`・`cd frontend && npm run lint` がいずれもエラーなく終了する。人間が配布ビルドの画面を目視し、3D 散布図の改善を承認する。
- **`depgraph-density`**: 配布ビルドの依存グラフの枠に 10 個より多いノードが描かれ、ノードが円周上の等角配置になっておらず、密な領域と疎な領域が見分けられる。ノードとエッジの更新が引き続き起きる(30 秒間の観察で表示の変化が 1 回以上ある)。`go test ./...` に、ノード数が 10 より多いこと、および隣り合うノードの角度間隔または中心からの距離が一様でないことを検証するテストが含まれ成功する(現状の等角配置に対しては失敗するテストであり、配置の算出が Go 側にあることの検証を兼ねる)。`wails build -devtools` のビルドで `window.nullops.enableFrameStats()` を呼んで計測し、計測対象の 5 パネルの p95 がいずれも 20 ms を超えない。`go vet ./...`・`go test ./...`・`cd frontend && npm run lint` がいずれもエラーなく終了する。人間が配布ビルドの画面を目視し、依存グラフの改善を承認する。

## 2. 未確定

- **3 点を入れた後になお残る「単調さ」の要因**: 要求は配置・3D 散布図・依存グラフの 3 点を単調さの要因として挙げている(request.md §1)が、3 点を入れた実画面を見るまで、それ以外に要因が残るか・残るとすれば何かを問いの形にできない。全 unit の完了後に配布ビルドを見て初めて問いを立てられる(立てられれば別 roadmap の候補にする)。
- **p95 が 20 ms を超えた、または境目付近に出たときの対処**: どの unit のどの要素(ノード数・軸線・描画面積)を削るか、ログストリームが主スレッドを占める影響(他 5 パネルの間隔の悪化として現れる)を切り分けるか、あるいは計測器の弱点(Web インスペクタ接続下で測ることの影響。凍結済みの `005-framestats-runtime/spec.md` §8.1 が残した論点)を先に潰すかは、実測の結果が出るまで問いの形を定められない。各 unit の計測で超えた時点で、その unit の中で問いを立てる。

## 3. スコープ外

- **Windows・Linux での確認**: 依頼者が macOS のみと定めた(request.md §4)。
- **3D 散布図のホイールによるズーム**: 投影に距離の概念を導入する変更になり、回転の操作だけを入れるという承認済みの決定(request.md §4・§5)に反する。
- **3D 散布図以外のパネルへの操作の追加**: 依頼者が明示した(request.md §4)。操作を持つのは 3D 散布図だけとし、他のパネルは放置して眺める性格を保つ。
- **パネルの追加・画面の切り替え・設定 UI**: 依頼者が明示した(request.md §4)。目的は既存 6 パネルの見え方の改善であり、画面の増設はその外である。
- **擬似データの生成方式の変更**: Go 側が生成しフロントエンドが写像する分担は保つと依頼者が定めた(request.md §4)。依存グラフのノード数と配置の変更は、この分担の中で行う。
- **`wails dev` でホットリロードが効かない件**: 既知で実害がホットリロードの停止に限られ、依頼者が対象外と定めた(request.md §4)。本 roadmap の確認は配布ビルドで行うため影響しない。
- **ログストリーム・コミットグラフ・折れ線グラフ・タコメータの中身の作り込み**: 依頼者が単調さの要因として挙げたのは配置・3D 散布図・依存グラフの 3 点である(request.md §1・§2)。これら 4 パネルは #1 で枠の大きさと位置が変わるだけで、描画の中身は変えない。
- **計測器(`framestats.ts`)の改修**: 判定は既存の計測器で行うと依頼者が定めた(request.md §3)。計測器の弱点への対処は「未確定」に置いた条件が成立したときに検討する。
- **描画の自動視覚検証(ブラウザ自動化等)の整備**: 依頼者が完了条件を人間の目視と定めた(request.md §3)ため、`001-dashboard-mvp` と同じく検証手段の自動化は目的の外である。
- **PR のマージとリリース**: PR の作成までを完了条件とし、マージは人間が行う(request.md §3)。

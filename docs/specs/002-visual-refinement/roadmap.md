# visual-refinement — 作業単位への分解

roadmap `001-dashboard-mvp` で動くようになった 6 パネルの画面を、作業中に見えるダッシュボードとして説得力のある見え方にする。配置は見出し無しの不均等な割り付けになり、3D 散布図は軸線を持ちドラッグで視点を変えられ、数千点の微細な点が地形・球・らせんの構造を作って高さに応じた色を持ち、背面と底面のパネル・格子・目盛りが視点と一緒に回り、依存グラフは疎密のあるノード配置になる。これらを macOS の配布ビルド(`wails build`)で人間が目視して承認でき、かつ既存の計測器で計測対象のパネルの p95 が 20 ms 以内であることを確かめられる状態にする。unit の切り方はこの状態から逆算している。

要求の本体は `docs/specs/002-visual-refinement/request.md` にある。本書は要求の内容を再記述せず、章番号で参照する(目的は §1、実装する 3 点は §2、roadmap 全体の完了条件は §3、スコープ外は §4、承認済みの決定は §5、既存コードの事実は §6)。言語規約・コーディング規約は `CLAUDE.md` にある。3D 散布図の見た目の目標(unit #3・#4)は、中継役から渡された参考画像 3 枚(request.md §2.2 の参考サイトの画面。2026-09-06)で定める。画像は第三者のサイトの画面であり、リポジトリには置かない。各 unit の仕様化では中継役が画像を再提示する。

- 色の規律は次のとおり扱う。凍結済み `002-scatter3d-panel/spec.md` Requirement 9.1(色は `globals.css` の `@theme` トークンから解決し、`.ts`・`.tsx` に色の直値を書かない)・9.2(解決に失敗したら既定の色へ退避)と、完了済み `002-scatter3d-controls/spec.md` Requirement 8.2(Requirement 9 の振る舞いを変えない)は #3・#4 でも維持する。一方、凍結済み `002-scatter3d-panel/spec.md` §6.5「新しいトークンは追加しない」は #3 の spec で置き換え、カラーマップの端点・中間点とパネルの面・格子・文字の色をトークンとして `globals.css` に足すことを許す。連続的な色は、マウント時にトークンを解決して補間した段階的なパレット(色文字列の配列)を 1 度だけ作り、毎フレームはそれを引くだけにする。段数が粗いと帯が見えて完了条件(隣り合う高さが見分けられる)と食い違うため、段数と目視の基準の関係は #3 の spec で定める。カラーマップの方式は「構造(地形・球・らせん)ごとに独立した色系統を持ち、地形の色系統は時間でゆっくり巡る」とし、そのために `ScatterPoint` へ構造の識別子(またはカラーマップ用の値)を足す契約変更と、複数のパレットを持つことを認める(2026-09-06 にユーザーが決定)。トークンの追加と直値の禁止の維持も同日にユーザーが確定した。
- unit #4 は、完了済み `002-scatter3d-controls/spec.md` §3 前提 1 のうち「格子(底面のグリッド)は線が増えて点の視認を妨げるため置かない」と、同 §2 対象外の「ラベル(軸名や目盛の文字)」(理由: 擬似データの値を読ませることになり眺める画面の性格から外れる)を反転する。反転は、参考画像に照らして「背面・底面のパネルと格子・目盛り・軸名」を入れるとユーザーが 2026-09-06 に決めたことに基づく。当時の理由が消えたわけではないため、#4 の spec は「格子が 1〜2 px の点を隠さない線の細さ・濃さ」と「文字を数値 4〜5 個と軸名 1〜2 語に留める」を受け入れ基準に含める。
- 3D 散布図の描画は Canvas 2D による自前投影で、WebGL・描画ライブラリは導入しない(凍結済み `002-scatter3d-panel/spec.md` §3 前提 1、§2 対象外)。参考画像は WebGL の実装(`002-scatter3d-controls/research.md` §1)であり、点数・発光・ぼかしをそのまま再現する対象ではなく、Canvas 2D と p95 の枠の中で近づける目標として扱う。

- 作業ブランチは `wip/visual-refinement`(request.md §6)。各 unit の作業ブランチはここから派生する。
- 知識 port は無い(`docs/dev/ports/` が存在しない)。
- 外部の参考(request.md §2.2 の参照 URL、§2.3 の Obsidian のグラフビュー、§2.1 の既存ダッシュボード)は各 unit の仕様化で調べる。本書では調べない。

順序は #1 → #2 → #3 → #4 → #5 とする。

- #1 を最初に置くのは、3 点のうち人間の決定(配置案の選択)を要する不確実性が最も高く、かつ他の 2 点の見え方を左右するためである。配置が決まらないと 3D 散布図と依存グラフの枠の大きさ(描画面積)が定まらず、軸線の見え方・ノードの疎密の見え方・描画の負荷のいずれも配置後に確かめ直すことになる。加えて、見出し行の削除は全パネルの枠(`Panel.tsx`・`page.tsx`)に触るため、#2〜#5 と同時に進めると同じファイルで衝突する。
- #2 を #5 より前に置いたのは、3D 散布図が当時視点を操作する口を持たず(request.md §6)、ポインタ操作・視点の状態・自動回転への復帰という新しい仕組みを WebView 上で成立させる不確実性が、既存の生成と写像の分担を保ったまま配置を変える #5 より高いためである。
- #3・#4 を #2 の後に足したのは、#2 の完了後にユーザーが配布ビルドを参考画像と見比べ、点の密度・色・構造・パネルの 4 点で参考に及んでいないと判断したためである(2026-09-06)。#2 は差し戻さず、#2 の成果(視点の状態機械・軸線・ドラッグ操作)の上に積む。
- 3D 散布図の残り 4 点(点の密度・カラーマップ・構造・パネルと目盛り)を #3 と #4 の 2 つに割るのは、1 つにまとめると要件が規模の目安(10 以下)を超える見込みであることに加え、性質が違うためである。#3 の 3 点(点数・色・構造)は互いに切り離せない。構造の無い雲に色を付けても面が読めず、数千点にしても構造が無ければ雲が濃くなるだけであり、点数の上限は、点ごとの色の切り替えを含む描画方法と、Go からフロントエンドへ毎秒 1 回送る経路(JSON の直列化・イベントの配送・受信側の解析。点数に比例して重くなり、1 回の解析が 1 フレームに集中する)の両方で決まる。したがって p95 を測りながら上限を決める作業は、3 点をそろえた状態で 1 度に行う。一方 #4(パネル・格子・目盛り・影・背景の地)は描画の追加であり、点群の生成・転送・着色を変えない。
- #3 を #4 より前に置くのは、#4 の目盛りの値と軸名が #3 が定める構造(高さの範囲と意味)に依存し、#4 の影の描画回数と格子の密度が #3 で確定した点数と p95 の余裕に依存するためである。
- 影の投影(点群を背面と底面へ淡く写す表現)を #4 に含めるのは、参考画像 3 枚すべてでパネルに投影が写り、パネルが「面」として読める主因が格子ではなく投影であるためである。格子だけのパネルは #2 の稜線と見え方の差が小さい。影は点の色を変えず単色の淡い塗りで足せるため、点ごとの色の切り替えを伴わず、点の間引きで負荷を調整できる。p95 が超えた場合の削る順は、影 → 格子の密度 → 点数とし、#4 の spec で定める。
- #3・#4 と #5 は、触るファイル群(Go の生成源・フロントエンドのコンポーネントとライブラリ)が重ならないため並行して進めてよい。ただしいずれも描画の負荷を増やすため(request.md §3)、後に完了する側の完了条件の計測は、先に完了した側を取り込んだビルドで行う。#5 を最後に置くのは、3D 散布図の作り込みを先に終えてから依存グラフへ移るためである(2026-09-06 にユーザーが決定)。
- 3 点の統合確認だけの unit は立てない。各 unit が配布ビルドの目視と p95 の計測を完了条件に持ち、後に完了する unit の計測が全体の統合確認を兼ねるため、その中身だけでは仕様化と承認の往復に見合わない。

### 1.1. 各 unit の完了条件

## 2. 未確定

- **3 点を入れた後になお残る「単調さ」の要因**: 要求は配置・3D 散布図・依存グラフの 3 点を単調さの要因として挙げている(request.md §1)が、3 点を入れた実画面を見るまで、それ以外に要因が残るか・残るとすれば何かを問いの形にできない。全 unit の完了後に配布ビルドを見て初めて問いを立てられる(立てられれば別 roadmap の候補にする)。
- **p95 が 20 ms を超えた、または境目付近に出たときの対処**: どの unit のどの要素(ノード数・軸線・描画面積)を削るか、ログストリームが主スレッドを占める影響(他 5 パネルの間隔の悪化として現れる)を切り分けるか、あるいは計測器の弱点(Web インスペクタ接続下で測ることの影響。凍結済みの `005-framestats-runtime/spec.md` §8.1 が残した論点)を先に潰すかは、実測の結果が出るまで問いの形を定められない。各 unit の計測で超えた時点で、その unit の中で問いを立てる。
